# Research: Third-party code by wrap

Facts checked 2026-11-12 against `oolite-dev` (branch tip of `develop` at the time), its build
directories, and the libraries' published sources. No expansion content was read. The spec's
*Context* already holds the inventory, the local-edit table and the API checks; this file holds
what the plan needed beyond them.

## What the build does today (measured)

- **Warning levels.** The game target builds at meson's `warning_level=1`: its compile lines carry
  `-Wall` and no `-Wextra` (`build/meson_dev/compile_commands.json`, `MyOpenGLView.cpp` and
  `Core/MiniZip/unzip.cpp`). `oofnd` overrides to level 2. QuickJS-ng builds at its own level 3
  plus the `-Wno-*` list in its own `meson.build`. QuickJS-ng's include directories are plain `-I`,
  not `-isystem`.
- **Options.** `default_library=shared` (meson's default), `wrap_mode=default`,
  `force_fallback_for=['quickjs-ng']`. QuickJS-ng is made static by the `default_options` on its
  `dependency()` call in `src/meson/meson.build`.
- **Unit tests link the game's dependencies.** `tests/unit/core/meson.build` builds each program
  from the game target's own objects (`extract_objects`) with `dependencies: oolite_dependencies`.
  So a library that becomes a dependency of the game reaches every test program with no further
  wiring. The loop asserts that every source a test names is in the game target, so the three
  entries that name `Core/MiniZip/unzip.cpp` and `ioapi.cpp` must lose them or setup fails.
- **The EXR signature is not fixed.** `OOSaveEXRSnapshot.cpp` writes a `signature` attribute of
  `"Generated by Oolite " + ctime(now)`. Two runs never write the same `.exr` bytes, on any version.

## R1. One wrap per library, named after its dependency

**Decision**: four wraps, `miniz.wrap`, `minizip.wrap`, `tinyexr.wrap`, `stb.wrap`. Each file's name
equals the dependency name it provides, so `force_fallback_for` and `dependency()` use one name
per library, as `quickjs-ng` does.

**Rationale**: `force_fallback_for` and `dependency()` name the same thing. Matching names avoid a
`[provide]` table that maps one to the other.

**Alternatives considered**: one `third-party` subproject holding all four (rejected in the spec:
four origins, versions and licences); `stb_image_write` as the name (rejected: the archive is the
whole stb repository and Debian's package is `stb`).

## R2. miniz: WrapDB 3.1.2-1 as published

**Decision**: install WrapDB's `miniz.wrap` (3.1.2-1) unchanged with `meson wrap install miniz`,
and request it with `default_options: ['default_library=static']`.

**Findings**: WrapDB's wrap fetches the `miniz-3.1.2.zip` release (amalgamated `miniz.c`), sets
`lead_directory_missing`, and overlays a `meson.build` that builds `library('miniz', 'miniz.c')`,
declares `miniz_dep` with its include directory and calls
`meson.override_dependency('miniz', ...)`. Its `project()` sets no `warning_level` or `c_std`.
On Windows it adds `-D_CRT_SECURE_NO_WARNINGS` and, where supported,
`-Wno-deprecated-declarations`.

**Hard rule 2**: those two flags are in WrapDB's packaging, which is downloaded, not in the fork's
tree, the same way QuickJS-ng's own `meson.build` brings its `-Wno-*` list. The fork adds none.
This is recorded as a decision Jon may override. The alternative is a custom wrap of the same zip
with the fork's own overlay and no suppression, accepting whatever warnings appear and patching
them (FR-006).

**MINGW_HAS_SECURE_API**: miniz 3.1.2's header no longer mentions it, and the amalgamated
`miniz.c` selects its stdio wrappers in code the excerpt checked did not show. M1 builds miniz
alone on UCRT64 with both compilers. If it fails or warns for lack of the secure CRT
declarations, the fix is a compile definition in the fork's `dependency()` call. A definition
that makes declarations visible is not a suppression. It is recorded in `data-model.md`.

**Alternatives considered**: a custom wrap with the fork's own overlay (kept as the fallback above).

## R3. MiniZip: zlib 1.4's `contrib/minizip`, nested under its own directory

**Decision**: `minizip.wrap` is a `[wrap-file]` of `zlib-1.4.tar.gz` with:

- `source_url` = the GitHub release asset, `source_fallback_url` = `https://zlib.net/zlib-1.4.tar.gz`
  (the spec's FR-002: WrapDB has no 1.4);
- `directory = minizip-zlib-1.4` and `lead_directory_missing = true`, so the archive extracts to
  `subprojects/minizip-zlib-1.4/zlib-1.4/…` and cannot share a directory with a future zlib wrap,
  which would extract to `subprojects/zlib-1.4/` (the spec's edge case);
- `patch_directory = minizip`: the overlay `subprojects/packagefiles/minizip/meson.build` lands at
  the subproject root and builds `zlib-1.4/contrib/minizip/ioapi.c` and `unzip.c` as a
  `static_library` against `dependency('zlib')`;
- `diff_files = minizip/0001-unzOpenCurrentFile3-reject-unsupported-method.patch`, paths relative
  to the subproject root (`zlib-1.4/contrib/minizip/unzip.c`).

**Rationale**: the overlay is the fork's own file, so it uses `static_library` directly and needs
no `default_library` option. The game already uses the system zlib, and MiniZip needs nothing
more. The nested directory keeps the tarball pristine and the overlay out of zlib's tree.

**To prove at M1**: meson 1.12.1 extracts a leading-directory archive under `lead_directory_missing`
as described. If it does not, the fallback is `directory = zlib-1.4` with the overlay at the
tarball root, and a comment in the wrap saying that a future zlib wrap must reuse this one.

**Hash**: taken at M1 from the downloaded archive and checked against the SHA-256 GitHub shows for
the release asset. zlib also publishes a detached `.asc` signature beside each tarball. Checking it
needs a key the setup does not hold, so it is not a gate.

**Alternatives considered**: WrapDB `minizip-ng` (different API, rejected in the spec); a system
`minizip` with wrap fallback (rejected: the system copy lacks the patch).

## R4. tinyexr: v3.4.0, the single header only

**Decision**: `tinyexr.wrap` is a `[wrap-file]` of GitHub's `archive/refs/tags/v3.4.0.tar.gz`
(`directory = tinyexr-3.4.0`), with `patch_directory = tinyexr`. The overlay `meson.build`
declares `tinyexr_dep` with `include_directories('.')`, which holds `tinyexr.h`, `exr_reader.hh` and
`streamreader.hh`, and `dependencies: dependency('miniz')`. It builds nothing.

**Findings**:
- v3.4.0's `tinyexr.h` declares every call `OOSaveEXRSnapshot.cpp` makes (spec *Context*).
- Its implementation section includes `exr_reader.hh` from the same directory, which includes
  `streamreader.hh`. `exr_reader.hh` is header-only and needs C++11.
- Its default ZIP backend is still miniz through `<miniz.h>`. `TINYEXR_USE_NANOZLIB`,
  `TINYEXR_USE_STB_ZLIB`, `TINYEXR_USE_ZFP`, threads and OpenMP default off.
- The new C11 library (`include/`, `src/`, CMake, vendored libdeflate, `deps/zstd`) is not
  referenced by `tinyexr.h`, and the overlay does not build it.

**To prove at M1**: `streamreader.hh` is header-only, and `OOSaveEXRSnapshot.cpp` builds at `-Wall`
on both compilers with no new warning. tinyexr's own `#pragma clang diagnostic` lines stay as the
author wrote them (spec edge case).

**Alternatives considered**: tinyexr's new C API (`exr_save_to_file`): a rewrite of Oolite code,
rejected in the spec.

## R5. stb: commit `48fb1c9` as a GitHub archive

**Decision**: `stb.wrap` is a `[wrap-file]` of `archive/<full 40-character hash of 48fb1c9>.tar.gz`
(`directory = stb-<full hash>`), with `patch_directory = stb`. The overlay declares `stb_dep` with
`include_directories('.')`. No patch.

**Findings**: stb has no releases, only commits. `48fb1c9` (2026-11-09) sets stb_image_write
v1.17. `02a8d35` (2026-11-08) rewrote `stbiw__linear_to_rgbe`: components ≤ 0 are written as 0, an
all-non-positive pixel as zero, and infinities are clamped to `FLT_MAX`. That covers Oolite's
clamp patch.

**Why a tarball, not `[wrap-git]`**: a git wrap is not cached in `packagecache`, so FR-012's
offline setup would fail. The full hash is resolved at M1 (`git ls-remote` or the commit page) and
written in the wrap with a comment giving the short hash and date.

## R6. How the libraries are requested

**Decision**: in `src/meson/meson.build`, beside QuickJS-ng (the exemplar), in this order:

1. `minizip` and `stb` on every host;
2. on Windows only, `miniz` (with `default_options: ['default_library=static']`) and then
   `tinyexr`.

All four are appended to `oolite_dependencies`. miniz is requested before tinyexr so its options
apply when tinyexr's overlay asks for it again.

**Rationale**: `oolite_dependencies` already reaches the game and every unit test (see *What the
build does today*). The Windows condition is the one `EXRSnapshotSupport/meson.build` has today
(FR-009).

## R7. The `force_fallback_for` list

**Decision**: the top-level `default_options` entry becomes a string built from a list written one
entry per line:

```meson
        'force_fallback_for=' + ','.join([
            'quickjs-ng',
            'miniz',
            'minizip',
            'stb',
            'tinyexr',
        ]),
```

**Rationale**: phase 2 then adds `'gtest',` as one line (FR-008, SC-008). `project()` already takes
computed values (`version: run_command(...)`). If the join is refused, M2 uses the dictionary form
of `default_options` (meson ≥ 1.2, within the 1.4 minimum) with
`'force_fallback_for': [ … one name per line … ]`. Either form keeps phase 2's change to a
one-line addition. M2 records which form is used.

## R8. Warnings and the hard-rule-2 checks

**Decision**:
- **Levels.** The fork's two library overlays (`minizip`, which compiles, and `tinyexr` and `stb`,
  which only provide headers) set no `warning_level`. They inherit the build's level (1, `-Wall`),
  the level the same code built at in `src/`.
- **Header-only libraries.** These compile inside Oolite's own translation units
  (`OOSaveEXRSnapshot.cpp`, `MyOpenGLView.cpp`), so they build at the game's flags.
- **No system includes.** Include directories stay plain `-I` (no `is_system`, no
  `include_type: 'system'`). This is the same constraint spec 005's plan takes for gtest.
- **The gate.** M0 records the sorted, de-duplicated `warning:` lines of a clean full build on
  Clang and on GCC. M2 does the same, and the two lists must match after removing lines whose path
  no longer exists. Any new line is fixed by a patch (FR-006) or stops the work.

## R9. The snapshot test

**Decision**: a new program `tests/unit/core/test_OOSnapshotWriters.cpp`, entry `['*']` (it needs
`MyOpenGLView.cpp`'s object for `stbi_write_hdr` and `OOSaveEXRSnapshot.cpp`'s for
`SaveEXRSnapshot`; `test_MyOpenGLView` uses `['*']` for the same reason). It is added at M0, before
anything moves, and must pass there. That pass on unmoved code is the "reference captured from
`develop`" of FR-011.

**What it checks** (contract: [contracts/snapshot-test.md](contracts/snapshot-test.md)):

- **Input.** One fixed 40×3 RGB float image (width ≥ 8 so stb uses its run-length scanlines),
  with zero, ordinary, negative, all-negative and large finite values (≤ 65504, the largest half).
- **`.hdr`.** The test decodes the file itself with a small RGBE reader, including run-length
  scanlines, that does not depend on stb. Each component must be within 1/128 of the pixel's
  largest input component of the input value clamped at 0. RGBE keeps 8 mantissa bits against a
  shared exponent, so one step is at most 1/128 of the largest component. Negative inputs must
  decode as exactly 0.
- **`.exr`, on Windows.** The file is decoded with tinyexr's own `LoadEXRImageFromFile` from the
  game object. Each half value must equal the input rounded to the nearest half, ties to even; the
  test does that conversion itself. The header parsed with `ParseEXRHeaderFromFile` must carry a
  `string` attribute named `signature` beginning `Generated by Oolite `.

**Rationale**: deriving the expected values from the input and the formats' rules, rather than
storing develop's output, avoids a capture mode that writes a test's own expectations. The
assertions are the same before and after the move, so passing on both is the comparison. Byte
comparison was never possible for `.exr` (the timestamped signature).

**If M0 fails**: if the old tinyexr does not round to nearest-even on some value, the expected
halves for that input are taken from develop's decoded output instead. They are recorded in the
test as literals with a comment, at M0 only, and never changed afterwards (hard rule 1). If the
`.hdr` bound fails on develop, the bound is wrong and the work stops for Jon. It is not widened.
