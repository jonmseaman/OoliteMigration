# Upstream #787: Fix intermittent macOS snapshot test failures

**Upstream:** David Hobley (hobleyd), merged 2026-11-05 as `4d788447a` · **In the stack:** base (an ancestor of `518520d43`); the stack replaces `tests/launch_snapshot.py` with its own readiness logic
**Verdict:** Ported with deviations

## What the PR changes

Only `tests/launch_snapshot.py`:

- After the handshake, send a harmless command (`'oolite-test-ready'`) and wait up to 90 s
  (`READY_TIMEOUT`) for its `command-result` before going on. The game reads commands only from its
  main loop, so an answer means the loop is running.
- Print how long the game took to answer.
- Keep the 5 s sleep for the title screen, then `takeSnapShot(); quit();` as before.
- Factor the macOS `sample <pid> 3` call into `sample_process()`, and also call it when the game
  never answers and when it does not exit after quit ("ignored the shutdown command").

## Findings

1. The two diagnostic `sample` calls #787 added are not at HEAD: a hang while waiting for the
   console answer, or after `quit();`, produces no stack sample on the macOS runner. This affects
   diagnosis only, not pass/fail. Evidence: `grep -n sample tests/launch_snapshot.py` → only `:572`;
   upstream hunks at `wait_until_ready` failure and `except subprocess.TimeoutExpired`.
2. The readiness probe differs in kind: HEAD uses Ping/Pong where #787 used a JS command and its
   `command-result`. Both are read and answered by the same client code on the main thread; HEAD then
   also requires game time to pass (`wait_until_rendering` evaluates JS), so by the time the
   snapshot is taken HEAD has proved more than #787 does.
3. `specs/002-seriesb-rebase-stack/upstream-prs.md` lists #787 as "not yet / T077"; it is in the
   base and the script at HEAD covers it, so that row is stale.

## Why this verdict

The behaviour #787 is for, not snapshotting until the game is actually running its main loop, is at
HEAD in a stronger form (a Ping round trip plus game-clock progress, with longer timeouts), so the
intermittent macOS failure it fixed is covered. What is lost is the extra `sample` diagnostics on two
failure paths, which is a deviation, not a regression of test behaviour. Not run here (Windows host;
the brief forbids running tests).
