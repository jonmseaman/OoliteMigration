**Upstream:** mcarans, merged 2026-11-05 as `568c2851e` (squash; first parent of the base merge `148575aab`) · **In the stack:** base
**Verdict:** Ported with deviations

## What the PR changes
- `build-all.yaml`: the `build-linux`, `build-windows` and `build-macos` jobs lose their `[deployment, test, dev]` matrix and build, test and package `deployment` only; `build-linux` is renamed `build-appimage`.
- Each of those jobs gains a "Test Oolite" step (`./mk.sh test deployment`), run when `github.event.pull_request.head.repo.full_name == github.event.pull_request.base.repo.full_name` (true on pushes and on same-repo PRs, false on PRs from forks); Windows prints `ntldd -R` on failure.
- `build-appimage` installs `zip`, zips `build/documentation/docs/assets/pdfs/*.pdf` into `oolite-documentation.zip` and uploads it as the `oolite-documentation` artifact.
- `test_builds.yaml` is deleted; its Ubuntu and Fedora jobs move into `build-all.yaml` as `build-ubuntu` (builds, tests and packages the `dev` flavour) and `build-fedora` (builds and tests the `test` flavour). The Arch, Windows and macOS test jobs are dropped, now covered by the release jobs' test steps.
- `release`: `needs` the renamed `build-appimage`; runs on `ubuntu-latest`; expects 6 artifact files instead of 11; publishes only the deployment installers, `space.oolite.Oolite-[0-9]*.flatpak` and the documentation zip.
- Flatpak runtime `25.08` → `26.08`; the weasyprint wheels move from cp313 to cp314; new GNUstep pins.

## Findings
1. **The release trigger is narrower than upstream's.** At the base, `release` runs when `github.event.pull_request.head.repo.full_name == github.event.pull_request.base.repo.full_name`: on every push to any branch of the repository and on every same-repo PR, each making a prerelease. HEAD (`.github/workflows/build-all.yaml:613`) runs it only on pushes to `master` or `develop`. Two consequences if this goes upstream as it stands:
   - Maintenance branches no longer release. Upstream has `1.92-maintenance` (`git ls-remote --heads https://github.com/OoliteProject/oolite.git` lists `refs/heads/1.92-maintenance`), and the release job's own cleanup steps still test `endsWith(github.ref, 'maintenance')` (`:653`, `:679`), which can no longer be true when the job runs. A maintenance branch cut from a master that has this workflow would build but never publish.
   - `develop` is a fork branch; upstream has none. On the fork, `develop` prereleases are never pruned, because "Remove old prereleases" and "Remove old workflow runs" run only for `master`/`*maintenance`.
   The narrowing is a deliberate fork decision (the commit message says feature branches should no longer publish prereleases). Before upstreaming, either restore upstream's condition or add `endsWith(github.ref, 'maintenance')` and drop `develop`. This is CI policy, not game behaviour.
2. **Same-repo PRs no longer build or test.** `clang-format-check` (`:18`), `oxp-upgrade` (`:33`), `build-ubuntu` (`:150`) and `build-fedora` (`:230`) are skipped on a PR whose head is in the same repository. `build-appimage`, `build-flatpak`, `build-windows`, `unit-tests-windows` and `build-macos` all `needs: clang-format-check` (`:50,307,343,451,550`) with no status-function `if`, so they are skipped too. Upstream's #788 test steps were written to run on same-repo PRs; they now run only on the branch push (the condition is true when `github.event.pull_request` is null). The push run tests the branch head, not the PR's merge with the target, so a same-repo PR's merge result is never built. Deliberate in `977698a93` ("its push already did"); worth stating in the upstream PR, since upstream maintainers open same-repo PRs.
3. `specs/002-seriesb-rebase-stack/upstream-prs.md` line 57 lists #788 as "not in the stack". That is stale: `git merge-base --is-ancestor 568c2851e HEAD` succeeds, and `568c2851e` is `148575aab^1`.

## Why this verdict
Deployment-only builds, the test steps, the folded-in Ubuntu/Fedora jobs, the documentation zip and the 6-file release are all at HEAD. The fork changes when the release and the PR jobs run (findings 1 and 2), which upstream would see as lost maintenance-branch releases and no CI on same-repo PRs. Neither is a game regression, so the verdict is deviations rather than regression.
