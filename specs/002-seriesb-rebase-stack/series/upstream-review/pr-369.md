# Upstream #369: Don't block an equipment installation if an incompatible item was installed but has since been removed

**Upstream:** dybal, merged 2026-09-12 as `2352401de` (squash) · **In the stack:** base (below the conversion); pinned by a new test in `f18e064bc`
**Verdict:** Ported correctly

## What the PR changes

- `Resources/Scripts/oolite-equipment-control.js`, `equipmentAdded`: the loop over
  `$equipmentEnabled` that removes items incompatible with the one just added now skips keys whose
  value is `0`. `equipmentRemoved` sets an item's entry to `0` rather than deleting it, so before
  the fix an item that had been installed and then removed was still "removed" again (a
  `player.ship.removeEquipment` call on something not fitted) whenever an incompatible item was
  added. That is the "blocked installation" in the title.

The PR touches nothing else; no engine code.

## Tests

`tests/unit/core/test_OoliteEquipmentControlScript.cpp` (registered at
`tests/unit/core/meson.build:19`, added in `f18e064bc` as `.mm`, now `.cpp`). It loads the real
script into a QuickJS-ng context with stand-ins for `EquipmentInfo.infoForKey` and
`player.ship.removeEquipment`, and checks three cases: installed-then-removed item is not removed
again when an incompatible one is added (the #369 case); an installed incompatible item is
removed; a compatible item removes nothing. Against the pre-#369 script the first check fails
(`removed` would be `'EQ_A'`).
