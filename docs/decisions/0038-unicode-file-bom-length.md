# ADR-0038 — `+stringWithContentsOfUnicodeFile:` reads exactly the bytes after a UTF-8 BOM

**Status:** Proposed — default in effect (Claude Code, frontier agent, bead oo-3rb.62, 2026-09-23;
ADR-0013). Jon may override.
**Date:** 2026-09-23
**Refines** [ADR-0034](0034-oofnd-strings.md) (its "found on the way" consequence). Implemented in
`upstream/oolite/src/oofnd/String.hpp` (`oo::str::decodeUnicodeFile`), called by
`src/Core/NSStringOOExtensions.mm`; tested by `tests/unit/oofnd/test_unicode_file.cpp`.

## Context

`+[NSString stringWithContentsOfUnicodeFile:]` (NSStringOOExtensions) loads JavaScript sources
(`OOJSScript`), text resources (`ResourceManager +stringFromFilesNamed:`) and debug-console
config (`OODebugMonitor`). After a UTF-8 byte-order mark it passed `length + 3` bytes starting at
`bytes + 3` to `-initWithBytes:length:encoding:`, so it read six bytes past the `NSData` buffer.
What those bytes are depends on the heap: a UTF-8 decode that includes them either fails (and
the whole file falls through to Latin-1, turning every non-ASCII character into mojibake) or
succeeds with six junk characters appended to the script. Neither outcome can be reproduced by a
replacement, and neither is deterministic in the game today.

No file shipped in `Resources/` or `DebugOXP/` starts with a UTF-8 BOM, so neither blessed golden
reaches the faulty branch.

### Measured (gnustep-base 1.31.1; throwaway probe running the category's body with `length - 3`)

- The UTF-16 branch hands the units after the first mark, **read little-endian whichever mark it
  was**, to `-stringWithCharacters:length:`, and GNUstep's mark handling runs twice over them: a
  leading U+FEFF is dropped, a leading U+FFFE is dropped and the rest byte-swapped, then the same
  again.
- The UTF-8 branch is strict (no overlong forms, no encoded surrogates, nothing above U+10FFFF,
  no truncated sequence) and GNUstep drops up to two further leading U+FEFF (never swaps).
- Otherwise every byte after the BOM is one Latin-1 character.

`oo::str::decodeUnicodeFile` reproduces all three over 60,000 generated byte strings with 0
differences; the unit test pins 40,000 of them by digest plus readable rows.

## Decision

1. **Fix the length to `length - 3`.** The undefined read is not reproducible and no golden
   depends on it; the fixed behaviour is what the category's comment and every caller intend.
2. **The decode lives in oofnd** as `oo::str::decodeUnicodeFile(bytes, length)` (and a `Data`
   overload), returning UTF-8 (WTF-8 for a lone surrogate). The category method becomes a shell:
   it still reads the file through `+[NSData oo_dataWithOXZFile:]` (the OXZ-aware reader has no
   oofnd form yet) and bridges the result with `oo::NSStringFrom`, which keeps every unit.
   Callers are unchanged; when their data moves to `oo::Data` they call the function directly.

## Consequences

- A script or text file saved with a UTF-8 BOM now loads as its bytes say, every time.
- This is an upstream bug; the fix is reportable to OoliteProject independently of the migration.

## Alternatives considered

- **Reproduce the over-read.** Impossible without reproducing heap contents; any "faithful" choice
  (always Latin-1, always junk) would be an invented behaviour, not the game's.
- **Leave the category on Foundation.** It blocks oo-qps either way; porting the decode now costs
  one function and pins GNUstep's mark handling while the probe can still be run.
