# ADR-0063: The GCC flavour, and what to do with GCC-only diagnostics

- Status: Accepted on recorded defaults by the orchestrator under Jon's 2026-10-20 delegation
  (items 4 and 5 decided 2026-10-21, docs/decisions/delegated-2026-10-19.md, bead oo-r3ffn; proposed
  by bead oo-1q4, batch BI, 2026-10-20).
- Date: 2026-10-20
- Beads: oo-1q4.2 (the tooling and src fixes), oo-1q4 (seam 4.3, "GCC build alongside the Clang build"), oo-lqd (Phase 4 exit gate)

## Context

The Phase 4 exit gate asks for a GCC build green beside the Clang one. Nothing had built this tree
with GCC since it left GNUstep. Measured with UCRT64 g++ 16.2.0 on main f49b3f049, a `test`-flavour
build (`-O2`, LTO, `-Wall`) gave 204 errors and about 1,000 warnings. Most were mechanical and are
fixed on the branch (item 2). What is left is GCC's flow-sensitive middle-end diagnostics firing
inside libstdc++ inlines on code that is correct, two of them in the oofnd unit tests, which build
with `werror=true`.

## Decision

1. **The GCC flavour is UCRT64's g++, built by `tools/build-windows.sh --gcc <flavour>` into
   `build/meson_<flavour>_gcc`** beside the Clang build. Not a MINGW64 environment: upstream's
   Windows CI is UCRT64-only, and one environment gives both compilers one set of libraries.
   mk.sh's per-flavour options, except **no LTO** (GCC's whole-program LTO fans each of ~170 test
   links out into parallel lto1 jobs, and type-checks the core tests' deliberate stand-ins as one
   program), plus three code-generation flags that bring GCC's output nearer Clang's and change no
   function's code: `-ffunction-sections -fdata-sections` with `-Wl,--gc-sections` (Clang's
   function-level linking), and `-fno-devirtualize-speculatively` (GCC's guessed direct calls
   added references a narrow core test cannot link, and diagnostics on paths that never run).
2. **First-party code GCC diagnoses is fixed where a behaviour-identical fix is natural**: a
   `= {}` default member initializer on a container of `oo::Ref<incomplete>` (GCC instantiates the
   destructor there), the printf format archetype (`OO_PRINTF_FORMAT`, `oofnd/PrintfFormat.h`:
   GCC on MinGW reads `printf` as Microsoft's), type-punning reads (`std::memcpy`), a signed /
   unsigned comparison, misleading indentation in the generated by-name table, a value read only
   after every scan succeeded (initialised), `NONNULL_FUNC` on two functions that assert their
   arguments (bead oo-1q4.2). The tests' side (`#import`, a deprecated GCC extension, to
   `#include` in 175 files; test_Entity's type-punned ivar access; test_OODebugMonitor's
   `~Ref<OOJSValue>` on an incomplete type; one misleading indentation) is on bead oo-1q4, to land
   with item 4 under std-2026-10-19 item 1 approval lines.
3. **A GCC false positive inside a libstdc++ inline on correct code is neither silenced nor coded
   around.** No `-Wno-*`, no pragma (hard rule 3), and no contortion of correct code to dodge a
   compiler's guess. They stay visible in the GCC build log. Measured on the branch:
   `-Wmaybe-uninitialized` on `std::optional`/`std::variant` resets and moves (OOConcreteTexture,
   OOCacheManager, OOShipGroup; test_OOPolygonSprite), `-Warray-bounds` on `initializer_list`s of
   `oo::PList` (OOCommodityMarket, OOOpenGLMatrixManager), `-Waggressive-loop-optimizations` on a
   `u16string::resize` (PlayerEntityStickMapper), and `-Wnonnull-compare` in `OOMatrix.h`'s
   `OOMatrixGetBasisVectors`, which is plain C that OOVoxel.c also compiles (hard rule 9).
4. **Decided 2026-10-21 (oo-r3ffn, recorded default): under GCC the oofnd suite builds without
   `werror`; under Clang it keeps it.** Two of those false positives are in oofnd unit tests built with
   `werror=true` (`test_plist.cpp` valueSemanticsDeepCopy: `-Wmaybe-uninitialized` on a moved
   `PList`; `test_ref.cpp` copyingAnObjectGivesAFreshCount: `-Wstringop-overflow` on a null path
   GCC invents), so the GCC build is not green. Recommended default: the oofnd suite keeps
   `werror=true` under Clang and drops it under GCC only (`src/oofnd/meson.build`), so the
   warnings still print and nothing is suppressed; the alternative is to respell the two test
   lines (an approval under std-2026-10-19 each), which batch BI tried and GCC still diagnosed.

5. **Decided 2026-10-21 (oo-r3ffn, recorded default): multi-draw arguments move into locals in
   Clang's order, the plain-C vector functions included; no golden is re-blessed.** The GCC game did not reproduce the goldens, because the game's random
   draws depend on argument evaluation order. Measured on bead oo-1q4.2 (batch BI): the GCC
   `test` build plays scenario 001 with the Rock Hermit elsewhere and as `rockhermit-chaotic`
   (4 differences from `goldens/windows-x64/001`). C++ leaves the order of a call's arguments
   unspecified; Clang evaluates them left to right and GCC (x86-64) right to left, measured with a
   three-argument probe (`mk(r(), r(), r())`: Clang 1 2 3, GCC 3 2 1). Upstream code draws random
   numbers inside one call's arguments in about fifty places (`make_vector(randf() - 0.5f,
   randf() - 0.5f, randf() - 0.5f)` in OOVector/OOHPVector's random vectors, Universe's colours and
   placements, OOParticleSystem, ...), so the blessed goldens are Clang's order. Recommended
   default: sequence those draws into named locals in the order Clang uses (behaviour-identical
   under Clang, and GCC then matches), as one bead, with the sites that are plain C (OOVector.cpp's
   and OOHPVector.cpp's vector functions; hard rule 9) named for Jon's yes; the alternative, a
   second set of goldens for the GCC build, is a re-bless and Jon's alone (hard rule 1).

## Consequences

`tools/build-windows.sh --gcc test`, `OO_CORE_BUILD=meson_test_gcc tools/check-core-tests.sh`
and `OO_APP_DIR=.../meson_test_gcc/oolite.app tools/tier-c.sh --only goldens` are the GCC gate
once items 4 and 5 are decided. Under GCC, libstdc++ makes `std::vsnprintf` MinGW's C99 printf
(`__USE_MINGW_ANSI_STDIO=1`); under Clang it is UCRT's, so the goldens on the GCC binary will also
be the check that the game's text formatting agrees.
